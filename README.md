# Ledger

A small ledger app: accounts, the debits and credits posted to them, and all-or-nothing bulk import of transactions from CSV. It's a code sample, so the focus is clean structure, careful validation and good tests rather than a long feature list.

**Stack:** Django 6 + Django REST Framework, Vue 3 + TypeScript (Vite) with PrimeVue, PostgreSQL 17, Docker Compose.

The full plan is in [plans/PLAN.md](plans/PLAN.md).

## What it does

- **Accounts:** open, edit and close accounts; search, filter and sort the list. Balances are credits minus debits, like a bank account.
- **Transactions:** post a debit or credit to an open account. A transaction can't be edited or deleted: you correct one by posting its opposite.
- **Bulk import:** upload a CSV of transactions for any number of accounts. Either every row posts, or none do and you get each row's problems, on screen and as a CSV you can fix and upload again. Every uploaded file is kept, exactly as uploaded, for auditing.

## Quick start

Prerequisites: macOS with [Homebrew](https://brew.sh). `make init` installs anything else that's missing: uv, [Volta](https://volta.sh) (Node version manager) and Docker Desktop. If it installs Docker Desktop, it opens it once so you can accept the license.

```sh
make init       # first time only: installs tools, Python 3.13, all dependencies, pre-commit hooks
make migrate
make seed       # optional: demo accounts, transactions and imports
```

Then run the two dev servers in separate terminals:

```sh
make backend    # Django API at http://localhost:8001
make frontend   # Vue app at http://localhost:5173
```

Or run the whole stack in Docker with `make up`.

| URL | What |
|---|---|
| http://localhost:5173 | The app |
| http://localhost:8001/api/docs/ | API docs (Redoc) |
| http://localhost:8001/api/schema/ | OpenAPI schema |
| http://localhost:8001/api/health/ | Health check: 200 when the API and database are up |

Ports are chosen to avoid clashing with other local projects: Postgres on **5433** (change `POSTGRES_PORT` and `DATABASE_URL` in `.env`) and the API on **8001** (to change it, pass the same `BACKEND_PORT=...` to both `make backend` and `make frontend`).

| `api-types` | Export the OpenAPI schema and regenerate the frontend's TypeScript types |
| `clean-coverage` | Delete coverage data files |

## Architecture

**Backend requests flow view → service → serializer.** Views are thin: they validate input with a serializer, call a service function, and return the result. Business logic lives in each app's `services.py` and knows nothing about HTTP.

**Errors have one shape.** Services raise `ApiError` (400) or `ConflictError` (409) from `core.exceptions`. The exception handler turns those, DRF's own errors and anything unexpected into the same response, and logs it (4xx as warnings, 5xx as errors with the traceback):

```json
{"error": {"type": "VALIDATION_ERROR", "message": "Invalid request data.", "fields": {"amount": ["..."]}}}
```

Unexpected errors become a generic 500; their details stay in the log. The API docs list the standard error responses on every endpoint automatically.

**The frontend's types come from the backend.** `make api-types` exports the OpenAPI schema and generates TypeScript types from it. Contract changes show up as a diff in `openapi.yml`, and type errors show up in the frontend.

Code conventions for both halves are in [CLAUDE.md](CLAUDE.md).

## Tooling

- **Python:** [uv](https://docs.astral.sh/uv/) manages Python 3.13, the virtualenv and the lockfile. Make targets run everything through `uv run`, so there's nothing to activate.
- **Node:** Volta pins the Node version in `frontend/package.json`.
- **Tests:** pytest-django with pytest-xdist and pytest-cov for the backend, Vitest and Vue Test Utils for the frontend.
- **Lint and format:** ruff for Python (linting, formatting and import sorting), ESLint, Prettier and a `vue-tsc` type check for the frontend, all run by pre-commit on every commit.
- **API types:** the frontend's TypeScript types are generated from the backend's OpenAPI schema with `openapi-typescript`.

## Design decisions

**The ledger is immutable, and nothing is deleted.** A posted transaction is never edited or removed; a mistake is corrected by posting the opposite transaction, as real ledgers do, so the history always explains the balance. Accounts are closed rather than deleted, and closing is final. In the database every foreign key is `PROTECT`, so even a stray delete can't take history with it.

**Balances are calculated, not stored.** An account's balance is the sum of its credits minus its debits, computed in the same query that loads the account (indexed on `account_id`). A stored balance would be faster to read, but it has to be kept in step with every write, and a bug there makes it silently wrong. At this scale the calculation is cheap, and it can never disagree with the transactions.

**Money is decimal everywhere.** Amounts are `Decimal(12, 2)` in Python and Postgres, and always positive: the sign comes from the direction (debit or credit). Amounts with more than 2 decimal places are rejected, never rounded. In the browser, money is never a JavaScript number: amounts stay decimal strings from the API to the screen, and `Intl.NumberFormat` formats the string exactly.

**One currency: USD.** Every amount is in US dollars. Multiple currencies would need a currency per account, exchange rates and rules for mixing them, which is a different app.

**Reposting is safe.** Every transaction has a `reference_id`, unique per account: the source system's ID, or a generated one. Posting the same reference twice is a 409, not a duplicate, so a retried request or a re-uploaded file can't post anything twice.

**Imports are all or nothing.** Every row is validated, and every problem is reported, not just the first. If any row is invalid, nothing is posted; otherwise every row posts together. A partial import would leave the user working out which rows made it in. Validation only reads, so it runs without locks, however long the file. Only the write at the end locks the file's accounts: it re-checks anything that could have changed in the meantime (an account closed, a reference used) and inserts every row in one `bulk_create`. For 10,000 rows, validation takes about 1.5 seconds and the locks are held for about half a second. Each import does the same number of queries however many rows it has.

**Imports are synchronous.** A 10,000-row file imports within the request, in about 2 seconds, so there's no worker queue (Celery or RQ) to run, monitor and deploy. If files grew much larger, the same service could move to a background job, with the import page polling its status.

**The URL holds the page state.** Search, filters, sorting and the page number live in the query string, so refresh, Back and shared links show the same view. Invalid values are ignored, and a page that no longer exists falls back to page 1.
